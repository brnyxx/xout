## 1. 관점별 평가

### 관점 A - CLAUDE.md 실전 적용성: 5/10

현재 산출물은 축당 무조건부 한 문장, 총 8줄이다:

```
먼저 실행한 뒤 변경 내역을 요약해 보고한다.
요청받은 범위 밖의 파일은 수정하지 않는다.
에러가 나면 원인을 고쳐 통과할 때까지 진행한 뒤 결과를 보고한다.
...
```

실제 프로덕션급 CLAUDE.md(예: 이 사용자의 글로벌 CLAUDE.md)와 비교하면 차이가 명확하다.
실전 규칙은 거의 전부 **조건부**다: "push 전에는 반드시 typecheck+lint+build",
"파괴적 작업은 확인 후", "히스토리에 conventional prefix가 보이면 그 스타일을 따른다".
무조건부 한 줄은 카테고리 선언이지 행동 계약이 아니다.

더 나쁜 건 **무조건부라서 위험한 조합**이 존재한다:

- `act_then_report` + `self_heal`을 같이 뽑으면 "물어보지 말고 실행하고, 에러 나도
  통과할 때까지 스스로 고쳐라"가 된다. DB 마이그레이션이나 삭제 작업에서 이 규칙
  그대로면 사고 유도문이다.
- `proactive`(발견한 개선점을 같은 변경에 포함)는 리뷰 diff를 오염시키는 안티패턴으로
  실무에서 자주 금지되는데, 무조건부로 켜진다.

판정: 지금 8줄은 "적용해도 해가 없는 수준"이 아니라 "일부 조합은 적용하면 해로운 수준".

### 관점 B - 측정 타당성 (판별력/일반화): 4/10

**모든 긋기 증거가 단일 장면에서 나온다**: "페이지네이션 off-by-one 수정"
(scene_skeleton.json, scn-pagination-fix 1개). 15번의 X 전부가 같은 저위험 버그픽스
맥락 안의 선택이다.

- 자율성 선호는 맥락 의존적이다: 버그픽스에서는 act-first를 원해도 스키마 변경에서는
  ask-first를 원하는 사용자가 다수다. 단일 장면 증거로 "먼저 실행한다"를 전역 규칙으로
  일반화하는 것은 측정이 주장을 지지하지 못하는 구조다.
- 제품 스스로 grade(판별시험/미시험)로 정직하게 라벨링하는 건 훌륭하지만, 라벨이
  정직해도 산출 규칙이 전역 무조건부인 이상 과일반화는 그대로 사용자에게 전달된다.
- 2축(response_language, verbosity)은 아예 긋기 없이 mined-prior로 들어온다.
  8축 중 2축이 "물어보지도 않은 추정"인 건 "2분에 규칙 8줄" 카피와 긴장 관계다.

### 관점 C - 축/값 설계 품질: 5/10

- `commit_style`은 서로 다른 두 결정을 한 축에 욱여넣었다: "자동 커밋 여부"(권한 문제)와
  "메시지 포맷"(스타일 문제). no_auto_commit을 고르면 포맷 선호를 표현할 곳이 사라진다.
- `comment_doc`의 `thorough` 예시는 자명한 줄에 주석을 다는 코드다
  ("# 1-기반 페이지 번호를 0-기반 시작 인덱스로 바꾼다"). 요즘 실무 기준으로 이건
  선택지가 아니라 slop이어서, 사실상 3지선다가 2.5지선다다.
- 실전 CLAUDE.md에서 가장 레버리지 높은 축들이 카탈로그에 없다:
  **완료 전 검증 규율**(빌드/테스트 돌리고 나서 완료 선언), **의존성 정책**(새 패키지
  추가 전 확인), **비밀정보 취급**. 이 셋은 거의 모든 프로덕션 CLAUDE.md에 있는데
  xout은 측정하지 않는다.

### 관점 D - 경쟁 제품 대비: 지금은 못 이긴다

- ouroboros: 인터뷰로 태스크별 스펙을 생성 - 산출물이 풍부하고 맥락적.
- paperthin: 즉시 체감되는 단일 가치.
- xout의 차별화 자산은 "설문이 아니라 반증(행동 비교)으로 선호를 측정한다"는 메커니즘과
  로컬/롤백/원장 엔지니어링인데, **산출물 8줄이 빈약해서 메커니즘의 우위가 결과물 우위로
  이어지지 않는다.** 메커니즘이 이기려면 산출물이 "손으로 쓴 것보다 나은 CLAUDE.md 조각"
  이어야 한다.

### 관점 E - 채널 (웹 GUI vs TUI/CLI): 지적이 맞다

현재 웹 브라우저 강제는 타겟(터미널에 사는 개발자)과 어긋난다. 다만 세션 엔진
(events/state/counter)은 UI 독립적이어서 채널 추가 비용이 낮다:

1. **TUI를 기본으로**: `xout` = 터미널 인터랙티브 세션 (stdlib만으로 가능 - 페어 출력
   후 1/2 키 선택. curses 없이 라인 기반이면 Windows 포함 전 플랫폼 동작, 서드파티 0 유지).
2. **웹은 옵션으로 강등**: `xout --web` - 데모 GIF/공유용으로는 여전히 최강 채널.
3. **에이전트용 비대화 CLI**: `xout pair --json`(다음 페어 요청) +
   `xout strike <pair_id> <A|B>`(긋기 기록). 이러면 Claude Code 안에서 `/xout` 스킬이
   브라우저 없이 대화로 세션 전체를 진행할 수 있다 - 에이전트가 페어를 보여주고 사용자가
   채팅으로 고르는 흐름. 이게 진짜 차별화 포인트다 (경쟁 제품에 없는 "에이전트가 자기
   규칙을 세팅받는" 루프).

### 관점 F - 도그푸딩: 이 규칙을 소비하는 에이전트 입장에서

CLAUDE.md 규칙의 최종 소비자는 에이전트다. 에이전트 입장에서 규칙이 실제로 행동을
바꾸려면 **결정 지점에서 걸려야** 한다. 매 턴 실제로 마주치는 결정 지점은:

1. 지금 실행할까, 물어볼까 (매 턴)
2. 이 파일까지 고칠까 (매 편집)
3. 테스트를 돌릴까/쓸까, 완료 선언 전에 뭘 확인할까 (매 작업)
4. 커밋을 만들까, 메시지는 어떻게 (작업 끝마다)
5. 에러 났는데 계속 갈까 (예외 발생마다)
6. 주석을 달까 (매 편집)
7. 새 패키지를 깔까 (가끔, 그러나 사고 나면 큼)

현행 8축은 이 결정 지점들을 정확히 겨냥한다 - **축 선정 직관은 옳았다.** 문제는 문안이다.
에이전트 입장에서 규칙이 무력해지는 세 가지 경우:

- **어차피 무시해야 하는 규칙**: "에러가 나면 통과할 때까지 스스로 고친다"를 받아도
  파괴적 복구 앞에서는 안전상 멈춰야 한다. 무조건부 문안은 에이전트가 스스로 예외를
  발명하게 만들고, 그 순간 규칙의 예측가능성(이 도구의 존재 이유)이 죽는다.
  조건을 규칙에 명시해야 에이전트가 예외를 발명하지 않는다.
- **검증 불가능한 규칙**: "핵심 근거만 짧게 덧붙인다" 류는 준수 여부를 사용자가 판정할 수
  없다. 걸리는 규칙은 전부 관찰 가능한 행위다: 커밋이 생겼나, 테스트를 돌렸나, 물어봤나.
- **기본값과 같은 규칙**: "사용자가 쓴 언어를 따라 응답한다"는 이미 기본 행동이다.
  기본값을 재확인하는 줄은 컨텍스트만 차지한다.

**깎기 기준 (컴파일된 모든 규칙이 통과해야 하는 3문):**

1. 다음 세션의 구체적 결정 지점에서 행동을 바꾸는가?
2. 지켰는지 사용자가 관찰로 판정할 수 있는가? (반증 가능성 - 제품 철학 그대로)
3. 에이전트가 안전을 위해 예외를 발명할 필요가 없도록 조건이 문안에 있는가?

셋 중 하나라도 실패하면 그 규칙은 싣지 않는다. 8줄 채우기보다 "전부 걸리는 N줄"이
낫다 - 규칙 수는 목표가 아니라 결과여야 한다.

## 2. 재설계안 (콘텐츠 v2)

### 2.1 핵심 원칙: "무조건부 한 줄" -> "조건부 규칙 블록"

각 축 값이 1-3줄의 조건부 블록으로 컴파일된다. 재설계 문안 전문:

**autonomy (자율성)**
| 값 | v2 규칙 블록 |
|---|---|
| ask_first | 코드를 수정하기 전에 계획을 제시하고 승인을 받는다. 명백한 오타 수정 같은 자명한 변경만 예외다. |
| propose_then_act | 짧은 계획을 먼저 적고 곧바로 실행한다. 되돌리기 어려운 작업(삭제, push, 배포, 스키마 변경)만 승인을 기다린다. |
| act_then_report | 가역적인 변경은 먼저 실행하고 변경 내역을 요약해 보고한다. 되돌리기 어려운 작업(삭제, push, 배포, 스키마 변경)은 실행 전에 확인받는다. |

**scope_adherence (범위)**
| 값 | v2 규칙 블록 |
|---|---|
| strict | 요청받은 범위 밖의 파일은 수정하지 않는다. 범위 밖 결함을 발견하면 고치지 말고 보고만 한다. |
| adjacent_fix_ok | 요청 범위와 직접 맞닿은 결함까지만 같은 변경에서 고치고, 그 사실을 보고에 명시한다. 그 밖의 발견은 보고만 한다. |
| proactive | 작업 중 발견한 개선점은 같은 변경에 포함하되, 요청 범위와 부수 정리를 보고에서 구분해 적는다. diff가 요청보다 커지면 사전에 알린다. |

**test_discipline (테스트)**
| 값 | v2 규칙 블록 |
|---|---|
| test_first | 버그 수정은 재현 테스트를 먼저 작성해 실패를 확인한 뒤 고친다. 기능 구현도 테스트를 먼저 쓴다. |
| test_after | 구현 직후 같은 변경 안에서 테스트를 추가한다. 테스트 없는 변경을 완료로 선언하지 않는다. |
| on_request | 테스트는 명시적으로 요청받았을 때만 작성한다. 단, 기존 테스트가 깨지는지 확인은 항상 한다. |

**comment_doc (주석/문서) - 값 자체를 재정의**
| 값(신) | v2 규칙 블록 |
|---|---|
| minimal | 주석은 코드로 표현할 수 없는 제약과 이유에만 남긴다. 코드가 하는 일을 재서술하는 주석은 쓰지 않는다. |
| public_api | 공개 함수/클래스에는 docstring을 쓰고, 인라인 주석은 비자명한 로직에만 남긴다. |
| none | 요청받지 않은 주석/docstring을 추가하지 않는다. 기존 주석 밀도를 따른다. |

**error_behavior (에러 처리)**
| 값 | v2 규칙 블록 |
|---|---|
| stop_and_report | 에러가 나면 즉시 멈추고 원문 로그와 함께 보고한다. 로그를 요약하거나 가공하지 않는다. |
| retry_then_report | 일시적으로 보이는 실패는 한 번만 재시도한다. 그래도 실패하면 로그와 함께 보고하고 멈춘다. |
| self_heal | 테스트/빌드 실패는 원인을 고쳐 통과할 때까지 진행한다. 단, 데이터를 지우거나 외부 상태를 바꾸는 복구는 멈추고 물어본다. |

**commit_style -> 두 축으로 분리**
- 신설 `commit_consent`: no_auto(요청 없는 커밋 금지 - 워킹 트리 유지) / auto_on_green(검증 통과 시 커밋 생성) 
- `commit_format`: conventional(히스토리의 conventional prefix를 따른다) / narrative(변경 의도를 서술형 제목으로) - **공통 접미**: "리포에 이미 자리잡은 컨벤션이 있으면 그것이 우선한다."

**신설 축 후보 (실전 레버리지 최상위)**
- `verification`: 완료 선언 전 검증 - always_run(빌드/테스트를 실제로 돌리고 출력을 확인한 뒤에만 완료 선언) / on_risky(위험 변경만) / trust_static(정적 확인으로 충분)
- `dependency_policy`: 새 의존성 - ask_first(추가 전 확인) / prefer_existing(기존 의존성 우선, 불가피할 때만 추가 후 보고) / free(자유 추가)

### 2.2 다중 장면: 조건부 규칙을 "증거로" 만든다

장면을 1개 -> 3개로 늘린다:

1. **저위험 버그픽스** (현행 페이지네이션 장면 유지)
2. **신규 기능 구현** (테스트/범위/의존성 축의 판별력이 여기서 남)
3. **고위험 작업** (마이그레이션/일괄 삭제 - 자율성/에러 축의 조건부를 여기서 측정)

같은 축을 두 장면에서 긋게 하면, "버그픽스에선 act-first / 마이그레이션에선 ask-first"라는
**조건부 규칙이 추정이 아니라 실제 긋기 증거에서 컴파일된다.** 이게 재설계의 핵심이자
설문형 도구가 흉내 못 내는 차별화다. 세션은 15긋기 유지(장면당 5긋기), 시간 프레이밍
"2분"도 유지 가능.

### 2.3 깎기 기준의 적용 결과 (관점 F의 3문 통과 목록)

- **통과 (측정하고 싣는다)**: autonomy, scope_adherence, test_discipline, error_behavior,
  commit_consent(신설 분리), verification(신설), dependency_policy(신설), comment_doc(재정의 후)
- **탈락 (규칙에서 뺀다)**: response_language(기본값 재확인 - 설치 시 사실 질문으로 이동),
  verbosity 중 "balanced"류 문안(검증 불가 - 관찰 가능한 문안으로 재작성해야만 유지:
  예: "결론을 첫 문장에 쓴다"는 관찰 가능, "핵심 근거만 짧게"는 불가),
  commit_format(리포 히스토리가 항상 우선이라 개인 선호의 효력이 낮음 - 부속 옵션으로 강등)

### 2.4 mined-prior 2축 처리

response_language는 긋기 없이 넣을 거면 규칙에서 빼고 설치 시 1회 질문으로 이동
(locale은 반증이 아니라 사실 확인의 영역). verbosity는 장면 2에서 실제 페어로 승격.
"묻지 않은 추정 규칙" 0개가 목표 - "2분, 규칙 N줄" 카피의 정직성이 완성된다.

### 2.5 구현 영향 범위 (예고)

- RULE_TEXT/카탈로그 v2 + 픽스처 팩 v2 (봉인 다이제스트 재생성, prereg는 v2 문서로 갱신)
- scene 2-3 픽스처 신작, scoring의 장면 축 판별 로직 확장
- TUI 세션 루프(stdlib 라인 기반) + `pair --json`/`strike` 비대화 명령
- ground_truth 정답표 v2 재작성
- 기존 테스트 계약 갱신 (규칙 문안 단언 다수)

작지 않다. 하지만 전부 세션 엔진(events/원장/원자적 착지) 위에서의 콘텐츠/채널 교체라
엔진 재작성은 없다.
